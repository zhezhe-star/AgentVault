# 项目背景

## 事件：OpenCode 密钥泄露

2026 年 10 月 16 日晚，开源 AI 编程助手 OpenCode 遭遇安全事件。次日，受影响用户收到标题为 “Action Required: Potential provider key breach” 的邮件。OpenCode 表示，有人未经授权访问了一套正处于停用流程中的遗留系统，保存在用户工作区里的第三方服务商 API 密钥可能已经暴露，其中明确点名 OpenAI 和 Anthropic。

根据公开报道：

- 官方称受影响范围约为 OpenCode Console 用户的 1.4%，仅涉及绑定外部服务商的 Console 用户。
- 多名用户在收到通知前，先收到 OpenAI 或 Anthropic 的异常用量提醒。
- 有用户报告 Anthropic 账户出现约 400 美元的非授权扣费；另有 Google Cloud 项目产生约 200 欧元费用，并被判定为滥用后暂停；最严重的个案据称高达 1700 美元。
- Anthropic 后续确认已强制注销所有疑似泄露的 Claude 密钥。
- OpenCode 表示正在与 Anthropic、OpenAI 和 Google 合作补救，具体入侵路径和更多细节待后续技术报告披露。

来源：[OpenCode密钥泄露：攻击者没写一行代码，何以一夜清空API账户](https://mp.weixin.qq.com/s/duGA63z9QHe0a6CLdvW8XA)

## 为什么这个事件和 AgentVault 直接相关

OpenCode Console 这类平台的价值是“集中管理”：用户把多家服务商的 API 密钥汇聚到一处，以换取路由、计费和审计等能力。但这也会把密钥托管的信任集中到同一个控制面。攻击者不需要逐个攻破最终用户，只要拿下这个聚合点，就能在短时间内用受害者的身份调用计费 API，把预付额度转化为真实账单损失。

这次事件还说明，“准备下线”的系统依然可能保存有效凭据和访问入口。如果退役流程没有包含凭据强制失效、入口关闭和数据清除，它就会脱离日常监控，但仍然保留攻击面。

另一个关键教训是：当密钥泄露后，修改平台登录密码或在客户端删除配置，并不能让已经流出的服务商 API 密钥失效。有效止损必须在服务商侧吊销旧密钥，然后签发新密钥并更新所有依赖方。这个过程越慢，损失窗口越长。

## AgentVault 的定位

AgentVault 要管理 AI 应用和 Agent 使用的第三方服务商 API 密钥，把“密钥托管”从单点信任变成可隔离、可观测、可快速恢复的凭据基础设施。

### 目标能力

1. **提供商密钥管理**
   - 管理 OpenAI、Anthropic、Google、火山方舟等模型服务商密钥。
   - 支持按应用、Agent、环境、团队或工具分配独立密钥，避免跨项目复用。

2. **泄露防护**
   - 对密钥进行加密存储和最小范围授权。
   - 记录密钥用途、依赖方、使用位置和最近使用时间。
   - 提供用量、费用和异常调用的监控与告警。

3. **一键切换与止损**
   - 密钥泄露或疑似泄露时，可以快速禁用旧密钥。
   - 将依赖方自动切换到备用或新签发的密钥。
   - 保留切换日志，便于事后确认哪些服务已经恢复。

4. **安全退役**
   - 工作区、项目或平台组件下线时，强制执行凭据失效、入口关闭和数据清理。
   - 退役动作可验证、可审计，避免“准备下线但仍有凭据”的灰色状态。

## 初步原则

- 一把提供商密钥尽量只给一个明确用途。
- 不把长期可用的高权限提供商密钥直接分散塞进各个配置文件。
- 任何密钥都必须有台账：谁创建、给谁用、用在哪里、何时轮换、何时吊销。
- 泄露响应的核心是服务商侧吊销与下游自动切换，而不是只改登录密码。

## 待确认事实

以下公开报道中的信息尚未得到官方完整确认，不能作为既定事实：

- 旧版 Console 是否明文存储密钥。
- 攻击者盗取密钥的确切动机是否为训练模型。
- 具体密钥总量、攻击者身份和完整入侵路径。
